Дать команде общую карту архитектурных подходов фронтенда, чтобы:

**Ключевая мысль доклада:** выбирай минимальный уровень, решающий текущие боли. Поднимайся выше, когда они появятся.

## Блок 0. Вступление (слайды 1–3)

**Слайд 1 — Титул.** Тема, докладчик, дата.

**Слайд 2 — Зачем архитектура: проблемы без неё.**
Что происходит в приложениях без архитектуры (или с плохой):
- **Высокая стоимость изменений** — одну правку приходится вносить в нескольких местах, и она ломает другое.
- **Замедление разработки** — каждая новая фича добавляется дольше предыдущей по мере роста кодовой базы.
- **Тяжёлый онбординг** — без явной структуры новому человеку (и AI-агенту) долго входить в проект.
- **Страх рефакторинга** — неясно, что с чем зацеплено, поэтому рабочий код боятся трогать.

Тезисы: архитектура — это **набор правил, который абсорбирует сложность** по мере роста. Нет «лучшей» архитектуры, есть подходящая под контекст.

**Слайд 3 — Чего мы хотим от архитектуры.**
К чему мы стремимся, выстраивая архитектуру (из принципов GRASP — ключевые для нас два):
- **Low Coupling** — модули минимально зависят друг от друга; изменение в одном не ломает остальные (слабая зацепленность *между* модулями).
- **High Cohesion** — внутри модуля собрано то, что логически связано; «код, который меняется вместе, лежит вместе» (сильная связность *внутри* модуля).

**Вывод слайда:** все методологии дальше — это разные способы добиться **low coupling + high cohesion**. Дальше смотрим на конкретные реализации этой идеи.

> 🖼️ **Картинка для слайда:** классическая матрица 2×2 coupling × cohesion (четыре варианта с кружками-модулями и связями между ними). Вставить изображение сюда. Ниже — ASCII-набросок ориентации осей, чтобы расставить варианты правильно:

```
                  High Cohesion ▲
                                │
                ┌───────────────┼───────────────┐
                │  ✅ ИДЕАЛ       │  ⚠️ так себе    │
                │  low coupling  │  high coupling │
                │  high cohesion │  high cohesion │
   low coupling ├───────────────┼───────────────┤ high coupling
        ◄───────│  ⚠️ так себе    │  ❌ хуже всего  │───────►
                │  low coupling  │  high coupling │
                │  low cohesion  │  low cohesion  │
                └───────────────┼───────────────┘
                                │
                  Low Cohesion  ▼
```

- **Левый верх — цель:** модули независимы, внутри каждого всё по теме.
- **Правый низ — антипаттерн:** всё связано со всем, внутри модуля каша.

## Блок 1. Уровни архитектуры приложения (слайды 4–11)

**Слайд 4 — Карта подходов: 3 группы по происхождению и масштабу.**

Прежде чем идти по уровням — общая картина, откуда что взялось:

- **1) Специфичные для фронта** — родились на фронте, для фронта: **Atomic Design**, **Feature-based** (популярный западный пример — **Bulletproof React**), **FSD**.
- **2) Пришли с бэка, адаптированы под фронт** — enterprise-наследие: **Layered / Clean / Hexagonal / Onion**, стратегический **DDD** (domain-oriented нарезка).
- **3) Уровень нескольких приложений** — не про один проект, а про систему: **Monorepo**, **Micro-Frontends**.

> Оговорки: группы 1–2 делят по **происхождению**, группа 3 — по **масштабу**, поэтому Micro-Frontends частично попадает и в «фронтовые». Flat structure — это «отсутствие подхода», вне групп. Деление — удобная карта, а не строгая таксономия.

Дальше идём **от простого к сложному** (ортогонально этим группам). Номер «уровня» — условность для порядка изложения, а не ранг: например, Atomic стоит на другой оси (организация UI), и его позиция в списке не значит «проще/слабее FSD». На каждом слайде: схема папок, плюсы/минусы, когда подходит.

**Слайд 5 — Уровень 0. Flat structure.**
```
src/
  components/   ← все компоненты вперемешку
  pages/
  hooks/
  utils/
  api.js        ← все запросы в одном месте
```
Группировка **по типу файла** (folder-by-type), без правил зависимостей — что угодно импортит что угодно.

- **➕ Плюсы:** минимальный порог входа и мгновенный старт; технологически независим (подходит любому фреймворку).
- **➖ Минусы:** нет правил зависимостей (границ); низкая масштабируемость — с ростом дорожают изменения и теряется навигация; применим только к маленьким проектам.
- **Когда:** прототип, MVP, ≤ 10 экранов, один разработчик.

**Слайд 6 — Уровень 1. Модульная организация (feature-based → domain-oriented).**

```
src/
  modules/
    billing/
      index.ts        ← публичный API (только это видно снаружи)
      ui/ model/ api/  ← приватные внутренности
    orders/
    catalog/
  shared/             ← UI-kit, утилиты, http-клиент (бизнес-агностично)
```

Режем код на **модули** (не по типу файлов). Две вариации на одной шкале: **feature-based** (по сценариям: `auth`, `cart`) → **domain-oriented** (по доменам: `billing`, `orders`); отличие — в строгости границ (кросс-импорты «на честном слове» → запрет через публичный API + линтер).

- **➕ Плюсы:** невысокий порог входа в большинстве вариаций; технологически независим (принцип организации, не привязан к фреймворку); хорошая масштабируемость — растёт от feature- к domain-варианту.
- **➖ Минусы:** границы держатся на договорённостях — без проверки линтером со временем размываются; много похожих, но разных вариаций — нет единого канона, риск разнобоя в команде.
- **Когда:** от небольшой команды (feature-based) до большого продукта с явными доменами — маркетплейс, банк, ERP (domain-oriented).
- **Оговорка для фронта:** берём нарезку + границы, но без DDD-механики Эванса (агрегаты, доменные события, репозитории) — бизнес-правила живут на бэке. FSD (далее) — родственная идея, оформленная как строгая методология.

**Слайд 7 — Уровень 2. Atomic Design.**
```
ui/
  atoms/      ← Button, Input, Icon
  molecules/  ← SearchField (Input + Button)
  organisms/  ← Header, ProductCard
  templates/  ← каркас страницы без данных
  pages/      ← страница с реальными данными
```
Самостоятельная методология (Brad Frost): организует **весь интерфейс** по уровню сложности — от примитива (atom) до целой страницы с данными (page).

- **➕ Плюсы:** технологически независим (применим в любом фреймворке); консистентный, переиспользуемый UI и единый язык с дизайном; невысокий порог входа — интуитивная иерархия от простого к сложному.
- **➖ Минусы:** область применения ограничена UI — не задаёт организацию состояния, данных и бизнес-логики; семантика слоёв оторвана от предметной области — «молекулы» и «организмы» слабо соотносятся с бизнес-требованиями, деление ощущается искусственным.
- **Когда:** UI-центричные продукты и дизайн-системы. Часто комбинируют с модульным/FSD: Atomic организует интерфейс, тот — бизнес-логику (нижние уровни `atoms`/`molecules`/`organisms` живут в `shared/ui`).

**Слайд 8 — Уровень 3. Feature-Sliced Design (FSD).**
```
src/
  app/        ← провайдеры, роутер, инициализация
  pages/      ← композиция виджетов и фич
  widgets/    ← самостоятельные блоки (Header, Sidebar)
  features/   ← сценарии (LoginForm, AddToCart)
  entities/   ← бизнес-сущности (User, Product)
  shared/     ← UI-kit, утилиты, http-клиент
              слайс: ui/ model/ api/ lib/ + index.ts
```
Развитие модульности с **жёсткими правилами зависимостей**: слои сверху вниз (верхний знает о нижних), публичный API слайса через `index.ts`, границы **проверяются линтером**.

- **➕ Плюсы:** высокая строгость границ (формальные слои + публичный API, проверка линтером); хорошая масштабируемость и предсказуемость; низкая связанность, лёгкий онбординг, постепенное внедрение.
- **➖ Минусы** *(это мой фаворит — тем важнее показать слабые места)*:
  - порог входа выше среднего — нужно освоить слои, слайсы и правила;
  - неоднозначность границ — размытая `widgets` vs `features`; связанные сущности на одном слое (`entities/order` не может ссылаться на `entities/user`, хотя `Order` его содержит);
  - хорошо ложится на React/Vue/Svelte, но с Angular сложнее — его собственная структура конфликтует со слоями FSD.
- **Когда:** средний/крупный SPA с умеренной логикой. Для тяжёлого домена — см. Clean.

**Слайд 9 — Уровень 4. Layered / Clean Architecture.**

> 🖼️ **Картинка для слайда:** концентрическая схема Clean Architecture (кольца изнутри наружу + стрелка «The Dependency Rule» внутрь). Вставить изображение на этапе отрисовки.

*Это семейство подходов с одной общей идеей:*
- **Hexagonal / Ports & Adapters** (Cockburn) — ядро общается с миром через интерфейсы.
- **Onion** (Palermo) — концентрические кольца, в центре домен.
- **Clean** (R. C. Martin) — синтез предыдущих + явное «правило зависимостей».

**Единый принцип:** бизнес-логика в центре и **ничего не знает** о UI, API, БД. Зависимости направлены **строго внутрь** — к более стабильному ядру.

*Где живут слои — два варианта (оба валидны):*
```
A. Глобальные слои            B. Слои внутри фичи (vertical slice)
src/                          src/
  domain/                       pages/
  application/                    home/
  infrastructure/                   domain/ application/
  presentation/                     infrastructure/ presentation/
  (домены внутри слоя:          shared/  ← те же слои, общие
   domain/order/, domain/user/)
```
- **A — глобальные:** слои на уровне приложения, домены группируются внутри слоя. Сильнее изоляция уровней.
- **B — vertical slice:** слои внутри каждой фичи/страницы, общее → в `shared`. Весь код фичи рядом, легко удалять (Vertical Slice Architecture, идея Jimmy Bogard).
- Имена слоёв — лишь **одно из соглашений**; число и названия колец не догма, важно правило зависимостей.

- **➕ Плюсы:** технологически независим — бизнес-логика изолирована от UI/фреймворка, легко заменить и переиспользовать (web + mobile); высокая тестируемость (ядро без UI и сети); высокая строгость границ (однонаправленные зависимости к центру).
- **➖ Минусы:** высокий порог входа — слои, порты/адаптеры, инверсия зависимостей; избыточен для простых приложений (домен вырождается в пустые типы); много кода и обёрток (маппинг между слоями).
- **Когда:** тяжёлая клиентская логика, кроссплатформа (shared core web + mobile), долгоживущий продукт.

**Слайд 10 — Уровень 5. Monorepo + Package-based (Nx / Turborepo).**
```
apps/ web/ admin/
libs/ feature-auth/ ui-kit/ domain-billing/
```
Архитектура задаётся графом пакетов и правилами импортов между ними (`enforce-module-boundaries`).

- **➕ Плюсы:** технологически независим — инструмент (Nx/Turbo) не привязан к фреймворку; высокая масштабируемость — переиспользование кода между приложениями, единые границы на уровне инструмента; быстрая сборка (кэш, инкрементальные билды).
- **➖ Минусы:** высокий порог входа — настройка инструментов и графа зависимостей; требует дисциплины версионирования и несёт риск «общего пакета на всё».
- **Когда:** несколько приложений, общий код, большие команды.

**Слайд 11 — Уровень 6. Micro-Frontends.**
```
host/               ← shell-приложение, собирает MFE вместе
  module-federation.config
mfe-catalog/        ← отдельное приложение (своя команда, свой деплой)
mfe-checkout/       ← отдельное приложение (может быть другой стек)
shared-ui/          ← общий дизайн-системный пакет
```
Несколько фронтенд-приложений, каждое **деплоится независимо** разными командами, возможно на разных стеках. Связь: Module Federation / Web Components / iframe.

- **➕ Плюсы:** максимальная технологическая независимость — каждое приложение на своём стеке; масштабируемость по командам — независимый деплой, автономия команд, изоляция отказов.
- **➖ Минусы:** очень высокий порог входа — оркестрация, общий рантайм, шаринг состояния между MFE нетривиален; операционная сложность — CI/CD на каждое приложение, риск рассинхрона UX.
- **Когда:** 10+ команд, разные жизненные циклы частей продукта.

## Блок 2. Как выбирать (слайды 12–13)

**Слайд 12 — Как выбрать подход + можно комбинировать.**

*Сначала — базовый выбор по масштабу приложения:*

| Масштаб | Базовый подход |
|---|---|
| **Маленькие** (MVP, лендинг, прототип) | Flat / Feature-based |
| **Средние** (один продукт, одна команда) | Feature-based, Atomic, FSD |
| **Крупные** (большой продукт, домены) | Atomic, FSD **либо** Clean (при тяжёлой клиентской логике) |
| **Из нескольких под-приложений** (много команд) | Monorepo / Micro-Frontends, внутри — любой из подходов |

> Оговорка: масштаб задаёт **базу организации**, а Clean — это про **изоляцию тяжёлой логики**, а не про размер. Большой проект может прекрасно жить на FSD без Clean.

*Главное — это не «выбери ровно одно»: подходы комбинируются.*
- Atomic силён в UI — его часто сочетают с модульным/FSD для бизнес-логики (Atomic для интерфейса + FSD для фич).
- FSD уже использует луковичный принцип Clean (зависимости направлены вниз, к стабильным слоям); при необходимости Clean применяют и точечно — для сложной доменной логики.
- Monorepo / Micro-Frontends — обёртки уровня системы; внутри каждого приложения живёт любой из подходов.

**Слайд 13 — Фактор AI и антипаттерны выбора.**

*Фактор AI (AI-assisted coding):*
- Жёсткая архитектура (FSD, Clean) стала ценнее: чёткие «полки» нужны не только людям, но и AI-агентам.
- Без границ AI генерит код разной гранулярности и ломает согласованность.
- Договорённости важно фиксировать машиночитаемо — и в линтере, и в правилах AI-инструментов (Cursor rules, CLAUDE.md): тогда их соблюдают и люди, и AI.

*Антипаттерны выбора:*
- Брать Micro-Frontends «на вырост» при одной команде.
- Тащить Clean Architecture в CRUD-лендинг.
- Спорить «atom это или molecule» вместо доставки фич.
- Внедрять FSD без линтера границ и культуры ревью.

## Блок 3. Итоги (слайд 14)

**Слайд 14 — Главные мысли.**
1. Архитектура — не цель, а инструмент. Важно это помнить.
2. Любая архитектура лучше, чем её отсутствие.
3. Сложность архитектуры должна догонять боль проекта, а не опережать её.
4. Комбинировать и видоизменять подходы — нормально; главное — **консистентность** внутри проекта.
5. AI-эра повышает ценность строгих границ.

→ Q&A: можно обсудить, какой уровень подходит нашим текущим проектам.
